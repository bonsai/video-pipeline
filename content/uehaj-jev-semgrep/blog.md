# 「grep を意味まで格上げする」って、実際どうなんだろう — jev-semgrep を触ってみた

TypeSafe AI の Jev っていう System One モデルが面白くて。**文章を生成せず、確率だけ返す**モデルなんです。
「この行はこの意味に合うか?」を yes/no の確率で答える。生成しない分、速いし安いし、判定がちゃんとしている。

それを使って作られたのが `uehaj/jev-semgrep`。**意味で探す grep** です。

## 「怒っている」を grep したい

素の grep で「怒っているお客さん」を探すのは、正直しんどいです。
「ふざけるな」「返金しろ」「最悪だ」……語の書き方を全部予想しないといけない。
しかも日本語と英語が混ざってる問い合わせファイルだと、もはや拷問。

jev-semgrep なら:

```sh
$ ./semgrep -n -e "customer is angry or frustrated" corpus.txt
14:ユーザー山田さんからの問い合わせ: 返金してほしい、商品が壊れていた
16:ユーザー佐藤さんからの問い合わせ: 注文した覚えのない請求が来ています。至急確認してください
18:I want my money back. The item arrived broken and customer service ignored me.
```

質疑応答ファイルのどの行にも「angry」も「frustrated」も無い。それでも拾ってくるんです。
英語の意味で日本語の行も引っかかる。**言語を問わない**のが地味にでかい。

## 原理がすごく腑に落ちる

これ、embedding(埋め込み)じゃなくて **cross-encoder 型**の判定なんです。
「行」と「質問」を同時に読んで、その行について**命題が成り立つか**を確率で返す。

だから、どちらも「返金の話」でも:

```
返金してほしい。商品が壊れていた       → "asking for a refund" 0.98
返金処理が完了しましたのでご確認ください  → 0.10
```

みたいな峻別ができる。「誰が」「求めている/済んだ」「否定」を全部見てる。
「スタッフが怒って電話を切った」は「顧客が怒って…」とコサイン類似度がほぼ1なのに、
Jev は主語で区別できる。ベクトルの「近さ」だけでは届かないところ。

そして意味ごとに独立した確率が出るから、**AND/OR/NOT がそのままブール演算**になります。

```sh
# 返金の話だけど、顧客が求めているのは除く
./semgrep -e "about a refund" -v "the customer is asking for a refund" contrast.txt
```

集合の引き算を「否定的な意味を足す」だけで書ける。これはきれいだなと思いました。

## 強いていうなら

- **検索した行は全部 TypeSafe の API に送られる**。社外に送りたくないファイルは要注意
- 確率は ±0.05 ぶれる。「あと少しで閾値」ぐらいのラインは慎重に
- 精度は英語 > 日本語。際どい条件は英語で書いた方が安定する
- 同じコーパスを何度も照会する構成なら、embedding 索引の方が安くて速い。
  「1回のふるい」が使いどころ

## 雑感

正直、一番「来たな」と思ったのは **1ファイル構成で依存ゼロ** なところ。
Node の `fetch` だけで動いて、30行まとめて送って8本並列、210行なら1秒弱。
「AIツールは何かと重い」みたいな既成概念を裏切る軽さです。

ツールの名前に注意点が1つ: 静的解析の [Semgrep](https://semgrep.dev/) とは**同名別物**。
うっかり `--config` 打ってもエラーになるだけだから、気をつけて。

ログ整理、問い合わせの仕分け、未テストコードのあぶり出し……「語じゃなく意味で探したい」局面に
刺さる道具。repo は GitHub で公開されてます(MIT)。
